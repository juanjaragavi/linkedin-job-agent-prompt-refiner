## **Context:**

This repository implements a safety-gated prompt refinement system for a browser-assisted LinkedIn job-search agent. The project does not treat prompt edits as a casual text transform. Instead, it records verified failure modes, generates minimal candidate revisions, validates them using static and adversarial checks, and requires human approval before a candidate can replace the active system prompt.

The codebase is a TypeScript + Node.js project structured around rule-driven generation and auditability. It includes a CLI refinement loop, an HTTP + SSE server for GUI access, a local MCP server for controlled autonomous tool use, and a web dashboard for reviewing issues, prompt history, and promotion decisions. The system is designed to keep the active prompt under human control while still supporting automatic candidate generation and static safety checks.

### Project Technical Audit

#### 1. Project purpose and operating model

The project centers on one primary artifact: the live system prompt in `prompts/linkedin-job-assistant.system.md`. That prompt governs a browser-based LinkedIn job-search assistant that handles profile-driven job searches, application workflows, credential validation, and interaction with external web flows. Because this prompt sits in a safety-critical path, the project enforces a closed-loop “issue → candidate → validate → approve” model instead of allowing direct edits without review.

The design pattern is intentionally fail-closed:

- Verified behavior problems are stored as structured issues.
- A candidate revision is generated by an LLM using only the issue evidence and minimal manual feedback.
- The candidate is passed through static checks before it may be considered further.
- The candidate is then re-evaluated adversarially to look for policy violations, unsafe phrasing, or unsupported capability expansion.
- Promotion requires an explicit human review and confirmation step, and the active prompt is backed up before replacement.

This makes the project more like a prompt governance or prompt control system than a generic agent scaffold.

#### 2. Repository structure and technology stack

The project is implemented in modern TypeScript and Node.js ESM, with the root package configured for CLI-driven refinement, local server startup, automated tests, and type checking.

Core runtime dependencies include:

- `@anthropic-ai/sdk` for model interaction
- `dotenv` for environment configuration
- `openai` for alternative provider integrations
- `zod` for validation layers
- `@modelcontextprotocol/sdk` for stdio MCP tooling

The application structure is split into a few distinct layers:

- `src/prompt-refinement/` — prompt issue handling, validation, evaluation, and candidate generation
- `src/mcp-server/` — local MCP server for safe file and command access
- `src/server/` — HTTP/SSE API server and app wiring
- `web/` — React + TypeScript GUI for prompt review and workflow management
- `prompts/` — the active system prompt and its safe-edit boundary
- `evaluations/prompt-refinement/` — issue and regression-case data
- `prompt-history/` — timestamped candidate prompts, audits, and diff artifacts

This structure supports both manual workflow governance and autonomous operation without weakening approval gates.

#### 3. Prompt governance and validation architecture

The prompt-refinement logic is implemented primarily in:

- `src/prompt-refinement/check.ts`
- `src/prompt-refinement/evaluator.ts`
- `src/prompt-refinement/refiner.ts`
- `src/prompt-refinement/types.ts`
- `src/prompt-refinement/providers/`

The safety logic is centered around `detectUnsafeCandidate()` and related static scanning routines in `refiner.ts`. These checks look for dangerous content such as:

- automatic or unconditional submission
- CAPTCHA, login, MFA, or anti-detection bypasses
- fabricated credentials, education, or authorization claims
- unsupported inference about sensitive or legal details

The validation layer is intentionally conservative. It matches risky phrases while recognizing negated clauses and gerund-based wording patterns, which helps avoid false positives on legitimate prohibitions like “never submit without explicit confirmation.” This is a meaningful implementation detail: the project’s safety logic is designed to defend against both unsafe candidate generation and accidental misclassification of guardrails.

`check.ts` adds a second, offline validation gate for prompt presence, prompt size constraints, and static safety checks. This keeps the system usable in CI or local workflows without requiring a live model call. The project treats validation as part of the product itself, not just a debug convenience.

#### 4. Refinement loop and issue-driven workflow

The refinement pipeline is driven by issue records written to `evaluations/prompt-refinement/issues.json`. Each item is expected to capture a concrete verified behavior problem:

- category
- severity
- evidence
- expected behavior
- observed behavior
- suggested fix

The CLI entry point is `src/prompt-refinement/cli.ts` and supports running the loop against a verified issue file. Examples in `README.md` and `USER_MANUAL.md` show the intended workflow:

1. Capture a verified failure or agent issue.
2. Add it to `issues.json`.
3. Run the refiner loop.
4. Inspect the generated report in `prompt-history/`.
5. Review the candidate diff against the current prompt.
6. Manually promote after confirming safety and regression coverage.

The `prompt-history/` output includes timestamped reports, candidate prompt snapshots, and audit artifacts. This is a core project principle: prompt changes are not ephemeral; they are recorded and recoverable.

#### 5. Provider abstraction and evaluation strategy

The provider layer supports model operations through a common interface while keeping model-specific logic isolated under `src/prompt-refinement/providers/`. This is especially important because the prompt-refinement system depends on both generation and adversarial evaluation. The evaluation step is logically separated from the refiner to avoid a single model pass becoming the sole safety gate.

The system uses a deterministic, low-temperature style for refinement (`temperature: 0` in the design), which improves consistency and reproducibility. The adversarial evaluator is used to assess whether a candidate truly improves the prompt without violating the project’s guardrails. The final decision is not automated; it is a reviewable, auditable outcome.

#### 6. Web dashboard and HTTP API

The project includes a web GUI under `web/` and a server layer under `src/server/`. The GUI is much more than a generic dashboard; it operationalizes the governance workflow:

- Dashboard for pipeline status and model metadata
- Prompt Editor for source and preview modes
- Issues management with schema validation
- History browser for audit and candidate artifacts
- Safety-first confirmation flow before writes or promotions

The server exposes a REST API and SSE stream that powers the GUI. It includes endpoints for:

- health checks
- log streaming
- active prompt retrieval
- prompt saves with two-step confirmation
- issue listing and mutation
- regression-case reads
- static prompt validation
- history browsing
- refinement runs
- promotion audits

This is a strong indicator that the project is built as a human-in-the-loop governance tool rather than a simple, one-off prompt file utility.

#### 7. MCP server and autonomous operation model

The `src/mcp-server/` layer provides a stdio MCP server intended for autonomous or semi-autonomous operation by a model host. It confines file access to the project root, allows selective command execution only after explicit confirmation, and logs every command to `logs/mcp-commands.log`.

The MCP server exposes operations such as:

- reading and editing files within project boundaries
- listing directories and searching files
- running shell commands only after human confirmation
- invoking prompt validation and prompt refinement tools
- supporting automated workflows while preserving approval control

This architecture is especially relevant for teams that want to allow an LLM to help manage the system while still enforcing a human-in-the-loop safety boundary.

#### 8. Regression coverage and prompt discipline

The repository places significant emphasis on regression coverage. `evaluations/prompt-refinement/cases.json` includes cases that cover issues such as:

- confirmation requirements
- submission gating
- authorization handling
- CAPTCHA protection
- salary floors
- duplicate detection

This matters because the project’s value is not only in generating better prompts but in reducing the likelihood that a candidate reintroduces a dangerous or non-compliant behavior. The repository therefore treats prompt quality as something testable and measurable, not just stylistically improved.

#### 9. Security and operational safety properties

The project’s safety posture is explicit and central to the design:

- never pass passwords, cookies, one-time codes, or sensitive account data into LLM prompts
- require explicit confirmation before irreversible actions
- base factual claims on the user profile or explicitly provided data only
- avoid stealth, evasion, or anti-automation instructions
- never claim a submission is complete unless the browser shows success
- preserve a backup of the active prompt before every write
- require human review for promotion

This gives the project a strong governance model under which model assistance is useful but not trusted to act unsafely.

#### 10. Current maturity and technical assessment

The project is a mature proof-of-concept and operational prototype, not a generic starter project. It demonstrates a real workflow for prompt governance in a domain where the cost of an unsafe system prompt is high. The architecture is coherent across CLI, API, web UI, and MCP layers, and the repository has explicit human approval gates, audit artifacts, and regression data.

Overall assessment:

- Strengths: clear safety model, strong audit trail, explicit verification workflow, modular project structure, human review enforcement
- Risks: model output remains inherently non-deterministic and must be reviewed; the system is narrow and domain-specific; operational safety depends on disciplined usage and valid issue capture
- Practical value: high for any workflow needing prompt-controlled autonomous behavior with strong reviewability and reproducibility

This repo is best understood as a prompt-governance platform for a high-risk browser automation assistant, with a robust safety loop and strong evidence-driven design principles.
